# Переход словарей и приложений на схему v2

Дата: 2026-09-30. Статус: план для реализации, не запуск миграции.

## Принятое решение

Одна актуальная схема исходников. Постоянный преобразователь v2 → v1 не
поддерживаем. Перед миграцией публикуем последний полный выпуск старого
формата, затем сохраняем его как замороженный совместимый выпуск.

Этап 1: `literally`, `links[]`, `forms_dict`. Конкретные типы связей,
грамматические признаки и уточнения целей ещё требуют утверждения.

Этап 2: постоянные id исходных статей, хеш содержимого, cefr, origin.
Этот этап остаётся в канале v2 при условии добавления необязательных полей
без изменения типов и смысла существующих обязательных полей.

Основной проект схемы: [av-ru-schema-evolution-plan.md](../../av-ru-schema-evolution-plan.md).

## Различаем версии

- Канал `/v2/` — поколение совместимости опубликованных данных/пакетов.
- Версия схемы исходной статьи — точный контракт JSONL.
- Версия SQLite и контракт вложенного JSON — мобильный формат хранения.
- Версия манифеста — структура `latest.json`.
- Версия словаря — выпуск содержимого.
- Версия приложения — установленный исполняемый клиент.

Не повышать версию манифеста только потому, что изменилась статья. Не считать
совпадающие числа доказательством совместимости. Во всех новых читателях
неизвестные необязательные поля игнорируются. Известные поля с неверным типом
считаются ошибкой, а не молча отбрасываются.

## Последний выпуск v1

1. Завершить согласованные исправления в исходниках и пересобрать av-ru.
2. Проверить схемы, поиск, ссылки, переводы, омонимы и повторяемость сборки.
3. Зафиксировать коммит и тег последнего старого выпуска; имя тега выбрать
   при выпуске. Записать SHA-256 файлов и версии опубликованных пакетов.
4. Пересобрать dev/ru, обновить бот, собрать последние старые мобильные базы.
5. Опубликовать последние совместимые архивы и проверить старые манифесты.
6. Сохранить старые `latest.json` и ВСЕ архивы, на которые они ссылаются,
   без переиспользования адресов для новых несовместимых пакетов.

Ждать загрузки на всех телефонах не нужно. Старое приложение при следующем
обращении получает последний совместимый выпуск. Дальнейших выпусков v1 нет.
Не повышать `min_app_version` в старых манифестах и не перенаправлять их в v2.
Старые приложения не обещают получать новые редакционные исправления.

## Пути публикации

Предлагаемый JSONL: `https://sources.avar.me/data/v2/av-ru.jsonl`.
Предлагаемые мобильные манифесты: `https://ios.avar.me/v2/latest.json` и
`https://android.avar.me/v2/latest.json`; архивы — внутри версионированного
канала, например `/v2/packages/<release>.zip`.
Точные имена и относительные пути утверждаются до переключения клиентов.

Нужно отдельно решить судьбу нынешнего `sources.avar.me/data/av-ru.jsonl`:
рекомендуется сохранить последний v1 там, а актуальный v2 публиковать отдельно.
Это замороженный файл, а не второе редактируемое семейство исходников.
Если выбрано переключение старого URL на v2, сначала перевести или закрепить
за v1 ВСЕ его известные автоматические потребители и объявить смену контракта.

## Порядок перехода

1. Утвердить контракт первого этапа и контрольные примеры.
2. Выпустить последний v1 по процедуре выше.
3. Подготовить сборку sources и клиентские изменения на локальных v2-образцах.
4. После ревью мигрировать исходники; опубликовать v2 по отдельному пути.
   Текущий приоритет источников не менять вместе со схемой без решения.
5. Проверить dev как первую площадку. Затем переключить ru и бот.
6. Выпустить новые SQLite-пакеты в новых мобильных каналах.
7. Выпустить приложения с новым URL и совместимой встроенной базой.
   iOS и Android можно выпускать независимо.
8. Следующие добавления второго этапа публиковать в v2 после проверки
   совместимости клиентов первого этапа.

До переключения автоматических сборок каждый сервис должен уметь принять
новый вход или быть закреплён за последним v1. Повторное получение нового
JSONL старым парсером может потерять поля, даже если JSON успешно читается.

## Сервисы и документы

В каждом соседнем репозитории файл `plans/schema-v2.md`:

| Репозиторий | Ответственность |
|---|---|
| sources | Схема, исходники, экспорты и координация |
| dev | Первая веб-площадка, парсер, поиск, HTML и TMA |
| ru | Производственный веб-клиент, проверка и переключение |
| tg_bots | Загрузка, поиск, форматирование сообщений |
| ios | SQLite и пакетный канал iOS |
| android | SQLite и пакетный канал Android |
| avarme-ios | Модели Swift, экраны и обновления приложения |
| avarme-android | Модели Kotlin, экраны и обновления приложения |

`../andriod` отсутствует; правильный существующий каталог — `../android`.
Отдельно инвентаризировать forms, corrector, index, multilang и внешние загрузки.
Им нельзя автоматически считать предоставленный этот набор документов.

## Проверки и откат

Общая выборка: обычное значение, буквальный перевод с пояснением, несколько
ссылок, омонимы, две формы одного падежа, формы разных классов и значений,
неразрешимая ссылка и необязательные будущие поля.

Проверять не только JSON-декодирование, но и доступность текста, буквального
перевода, ссылок, индекса форм и результатов поиска. Будущие id исходных
статей не заменяют автоматически уже генерируемые мобильные id.

До публикации проверить чистую установку и обновление поверх существующей
старой базы. Новый клиент должен либо поддержать старую базу при переходе,
либо безопасно использовать новую встроенную базу до скачивания v2.

Откат сайтов и бота: предыдущий код и закреплённый v1-вход. Откат мобильного
словаря: исправленный совместимый пакет с более высокой версией выпуска,
если автоматическое обновление допускает только рост номера. Старые архивы
сохранить, но не считать уменьшение версии рабочим автоматическим откатом.

Этот документ не авторизует деплой, публикацию приложений или изменение
кода потребителей; сейчас создаются только планы.
