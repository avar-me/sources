инструменты допустимы только если непосредственно помогают восстановить
границы или экспортировать уже выровненные статьи.

## Почему алфавитный порядок — основной сигнал

Словарь печатается в алфавитном порядке. Для предполагаемого заголовка `W`
между надёжными соседями `L` и `R` обычно выполняется:

```text
L <= W <= R
```

Это позволяет обнаруживать ошибки обоих типов.

### Ложная граница

OCR/segmenter принял русское слово, пример или продолжение глоссы за заголовок.
Такое слово часто не попадает в допустимый интервал между соседними настоящими
аварскими заголовками.

### Пропущенная граница

Внутри слишком длинной статьи находится выделенное/типографически похожее на
заголовок слово `W`, которое идеально попадает между предыдущим и следующим
надёжным заголовком. Это кандидат на отделение самостоятельной статьи.

Алфавитный порядок не является абсолютным доказательством: в книге встречаются
группировка производных, варианты написания, омонимы и исходные отклонения.
Поэтому он должен ранжировать и подтверждать границы совместно с геометрией,
но не автоматически переписывать данные в одиночку.

## 1. Построить единый выровненный поток статей

Создать один канонический артефакт, например:

```text
data/av-ru.1967.article_stream.jsonl
```

Одна строка — одна предполагаемая статья в физическом порядке книги. Минимум:

```json
{
  "article_id": "p0550-r-39732",
  "headword_raw": "*цебё",
  "headword": "цебе",
  "page": 550,
  "column": "right",
  "top": 397.32,
  "source_spans": [
    {"page": 550, "bbox": [0, 0, 0, 0]},
    {"page": 551, "bbox": [0, 0, 0, 0]},
    {"page": 552, "bbox": [0, 0, 0, 0]}
  ],
  "raw_text": "...",
  "current_entry": {},
  "current_outcome": "accepted|review|duplicate|dropped",
  "boundary_confidence": "high|medium|low",
  "boundary_reasons": [],
  "previous_article_id": "...",
  "previous_headword": "...",
  "next_article_id": "...",
  "next_headword": "...",
  "alphabet_relation": "in-order|equal|regression|uncertain",
  "boundary_decision": null
}
```

### Требования к `article_id`

- ID основан на физическом положении, а не на порядковом номере;
- ID не меняется после исправления текста заголовка;
- ID сохраняется при accepted/review promotion;
- при split новые ID получают suffix, например `...-a`, `...-b`;
- при merge сохраняются `merged_from_ids`.

### Важно

Этот файл должен включать accepted и review в одном потоке. Иначе алфавитные
«мёртвые зоны», где на странице нет accepted anchors, останутся невидимыми.

## 2. Реализовать правильный аварский sort key для boundary analysis

Использовать согласованный аварский алфавит, где диграфы являются отдельными
буквами:

```text
гъ, гь, гӏ, къ, кь, кӏ, лъ, тӏ, хъ, хь, хӏ, цӏ, чӏ
```

Перед сравнением применять только безопасную нормализацию:

- Unicode normalization;
- канонизация палочки;
- удаление звёздочки и служебной пунктуации заголовка;
- нормализация известной типографики ударения для сравнения;
- lowercase для sort key без изменения сохранённого headword.

Нельзя для сортировки молча заменять произвольное OCR-слово на ближайшее
словарное: это скроет именно те ошибки, которые нужно найти.

Добавить unit tests минимум для:

- всех аварских диграфов;
- слов с/без stress glyph;
- омонимов с одинаковым headword;
- дефисных слов;
- spelling variants;
- палочки разных Unicode forms.

## 3. Использовать локальный алфавитный интервал, а не только соседнюю пару

Текущий `check_order.py` фиксирует пары `prev > next`, но этого недостаточно.
Для каждого boundary candidate найти ближайший надёжный левый и правый anchor:

```text
trusted_left < candidate < trusted_right
```

Проверять окна минимум двух размеров:

- локальное: 2–3 статьи слева и справа;
- расширенное: до ближайших high-confidence anchors либо границы страницы.

Для каждого кандидата записать:

- входит ли он в интервал;
- насколько далеко выпадает;
- становится ли последовательность монотоннее при удалении кандидата;
- становится ли последовательность монотоннее при split текущего span;
- относятся ли одинаковые/регрессирующие слова к допустимому варианту,
  омониму или source grouping.

Нужен не только список regressions, но и ranked boundary suspicion score.

## 4. Искать ложные заголовки

Высокий приоритет кандидату на merge/removal, если одновременно выполняются
несколько сигналов:

- слово нарушает локальный алфавитный интервал;
- слово русское или похоже на русскую часть перевода;
- перед ним нет нормального завершения предыдущей статьи;
- bbox/font/indent слабее типичного заголовка;
- после удаления последовательность становится монотонной;
- предыдущая статья имеет оборванный перевод или пустой `ru`/`av`;
- raw fragment грамматически продолжает предыдущую статью.

Обязательно повторно проверить известные классы:

- sentence-initial Russian word (`у`);
- missed gloss continuation (`распятие`, `страна`, `осмеяние`);
- Russian declension marker `1-го скл.`;
- одинокие части примеров;
- номера, labels и cross-reference fragments.

## 5. Искать пропущенные заголовки внутри spans

Для каждого raw span, особенно длинного или нарушающего порядок:

1. собрать все слова/линии с headline-like typography;
2. включить suppressed segment candidates, которые текущая эвристика отвергла;
3. проверить, попадает ли возможный headword в алфавитный интервал;
4. проверить, образуются ли после split две содержательные статьи;
5. показать crop до/после предполагаемой точки split.

Особый приоритет:

- 528 `label-lookahead` items;
- 80 страниц, на которых они находятся;
- страницы без accepted anchors;
- spans с несколькими bold runs;
- spans, содержащие слова из современного `av-ru`, которых нет среди текущих
  headwords 1967 года;
- accepted/review статьи, на которые указывают unresolved links.

Современный словарь использовать только как hint, не как доказательство.

## 6. Решить dead-zone проблему глобальным контекстом

На страницах 97, 243, 332 и 417 уже найдены реальные split pairs, но там нет
accepted anchors. Нельзя вставлять их относительно случайной accepted статьи.

Для таких страниц anchors брать из общего article stream:

- последний надёжный заголовок на предыдущих страницах;
- первый надёжный заголовок на следующих страницах;
- running headers страницы, если они распознаны;
- общий допустимый алфавитный диапазон страницы;
- физический порядок колонок и строк.

Исправления внутри dead zone применять как согласованный блок. После блока
должен улучшаться или сохраняться глобальный порядок всего потока, а не только
accepted subset.

## 7. Не превращать алфавитный порядок в автоматическую дубинку

Перед автоматическим merge/split должны быть исключены или отдельно отмечены:

- одинаковые headwords/омонимы;
- `spelling_forms`;
- явно напечатанные source cross-reference stubs;
- подтверждённая группировка производных рядом с базой;
- заголовки с тяжёлым OCR, для которых sort key ненадёжен;
- перенос статьи через колонку/страницу.

Никакое исправление содержимого не делать только потому, что оно уменьшает
число regressions. Алфавитный порядок доказывает подозрение границы, но текст
подтверждается геометрией/PDF.

## 8. Создать одну boundary review queue

Вместо новых пересекающихся ledgers создать один ranked список поверх
`article_stream.jsonl`. Категории:

```text
probable-false-headword
probable-missed-headword
probable-wrong-carry
probable-column-order-error
source-order-exception
ocr-headword-uncertain
```

Для каждого item показывать:

- candidate и стабильный `article_id`;
- два соседа слева/справа;
- sort keys и объяснение нарушения;
- raw OCR текущей и соседних статей;
- bbox/crop точки границы;
- предлагаемую операцию: keep / split / merge-left / merge-right / rename;
- ожидаемую последовательность headwords после операции;
- `needs_pdf_review`.

Не создавать отдельную сложную веб-систему. Достаточно JSONL и простой HTML/
Markdown-проекции существующего review UI.

## 9. Провести конечный segmentation sprint

Порядок разбора:

1. Все high/high draft regressions — 131.
2. Все accepted regressions — 382.
3. Все 528 `label-lookahead` review items.
4. Все spans с более чем одним headline-like bold run.
5. Все page/column transition anomalies.
6. Остальные low/medium candidates, ранжированные suspicion score.

Один item может входить в несколько групп; считать уникальные physical
boundaries, а не сумму отчётов.

Для ускорения разрешается батчевое правило только после ручной проверки
репрезентативной выборки и negative sample. Цель — исправить повторяющийся
класс, а не формально классифицировать каждую строку.

## 10. Проверка качества границ

Создать небольшой human gold set, ориентированный именно на segmentation:

- минимум 20 целых страниц;
- по несколько страниц из начала, середины и конца словаря;
- страницы с высокой и низкой плотностью статей;
- multi-page entry;
- dead-zone pages 97, 243, 332, 417;
- страницы с известными false/missed headwords;
- случайная контрольная выборка без текущих findings.

Для каждой страницы вручную отметить только:

```text
позиция начала статьи → headword
```

Не вычитывать переводы на этом этапе.

Измерить:

- boundary precision;
- boundary recall;
- false split count;
- missed split count;
- page/column ordering accuracy.

Целевые значения перед Gemini:

- precision не ниже 99.5% на gold set;
- recall не ниже 99.5% на gold set;
- 0 необъяснённых ошибок порядка на gold pages;
- 0 пропавших physical boundary decisions.

Если gold set показывает более низкое качество, исправлять только найденный
класс segmentation errors и повторять тест. Не уходить снова в улучшение
семантического parser.

## 11. Подготовить экспорт для Gemini по 50 статей

После фиксации boundaries создать простой exporter, который берёт 50 соседних
строк из `article_stream.jsonl`. Каждый item должен содержать:

```json
{
  "article_id": "...",
  "page": 123,
  "headword_raw": "...",
  "headword": "...",
  "raw_ocr": "...",
  "current_entry": {},
  "previous_headword": "...",
  "next_headword": "...",
  "source_spans": [],
  "crop_paths": []
}
```

Экспорт обязан сохранять физически соседние статьи: контекст помогает Gemini
заметить остаточную ошибку split/merge.

Дополнительно сформировать инструкцию Gemini:

- исправлять только очевидные OCR-ошибки;
- не модернизировать аварское слово;
- не переписывать стиль словаря;
- не придумывать утраченный текст;
- различать `ocr_fix`, `boundary_issue`, `semantic_suspicion`;
- при сомнении ставить `needs_scan: true`;
- возвращать JSON с `article_id`, before/after и объяснением;
- не менять article IDs и порядок.

Первый pilot после этого батча:

- 50 случайных accepted articles;
- 50 приоритетных review articles;
- оценить precision предложений Gemini до масштабирования.

## 12. Жёсткий stop condition

Batch 6 считается завершённым, когда:

1. существует единый `article_stream.jsonl` с accepted + review;
2. у каждой статьи стабильный physical `article_id`;
3. source spans и соседние headwords доступны;
4. алфавитная проверка использует аварские диграфы и локальные anchors;
5. false-headword и missed-headword candidates собраны в одну очередь;
6. dead zones анализируются в глобальном диапазоне, а не только по accepted;
7. 20-page segmentation gold set размечен;
8. boundary precision и recall на нём не ниже 99.5%;
9. известные split pairs на страницах 97, 243, 332, 417 исправлены;
10. 131 high/high и 382 accepted regressions получили boundary decisions или
    были устранены; source-order exceptions доказаны по PDF;
11. 528 `label-lookahead` items прошли boundary triage;
12. exporter формирует детерминированные пакеты по 50 статей;
13. два clean builds остаются byte-identical;
14. после этого parser объявляется frozen.

После выполнения этих условий не создавать следующий parser batch. Начинать
Gemini pilot и исправлять OCR/языковые ошибки непосредственно в статьях.

## Ограничение объёма реализации

Чтобы снова не переинженерить задачу:

- максимум один новый builder/analyzer для article stream и boundary queue;
- максимум один exporter для Gemini;
- использовать существующие geometry, segment, draft и review artifacts;
- не вводить новый database/service/UI framework;
- не добавлять метрики, не влияющие на решение split/merge/keep;
- не пытаться достигнуть нулевых regressions за счёт allowlist без evidence;
- отчёт должен быть коротким: сколько boundaries проверено, сколько split,
  merge, keep и unresolved.

Главный deliverable этого батча — не новый код, а надёжный выровненный список
статей, который можно последовательно отдавать Gemini по 50 записей.
