# Инструкции для AI-ассистентов в этом репозитории

Этот файл — общая инструкция для Claude, Copilot, Cursor и других. Если вы агент — прочитайте до начала любых изменений.

## Что это за репозиторий

`sources.avar.me` — **источник правды** для всех данных экосистемы avar.me (словари, книги, корпусы). Сайт собирается из этих же данных и публикуется на GitHub Pages.

Другие репозитории (`forms`, `avar.me`, `corrector`, `index` и т. д.) при сборке выкачивают `data/*.jsonl` отсюда. **Они не правят данные у себя — они потребители.** Любые правки данных должны быть здесь.

## Главное правило

1. **Данные** (`data/*.jsonl`) — священная корова. Правки строго по запросу пользователя, обычно после обсуждения в Telegram-чате [@avarme_chat](https://t.me/avarme_chat).
2. **Не плодите данные.** Если в `data/` уже есть `av-ru.jsonl`, не создавайте `av-ru-v2.jsonl` — правьте существующий.
3. **Формат строк jsonl.** Сериализация только `json.dumps(obj, ensure_ascii=False)` — с пробелами после `:` и `,` (`{"word": "а", ...}`). **Никогда** не писать compact через `separators=(',', ':')`: это перетирает весь файл и делает бесполезный гигантский дифф. Править точечно (только изменённые строки); если без полной перезаписи не обойтись — каждая строка всё равно spaced, а `git diff --stat` не должен показывать перезапись всех ~N строк. Подробнее: [`.cursor/rules/jsonl-format.mdc`](.cursor/rules/jsonl-format.mdc).
4. **Оригиналы (PDF) — в `books/`.** Большие исторические сканы и оригиналы; ссылки на них в `sources.json` → `documents[]`. Не дублировать, не пересжимать.
5. **Не редактируйте `docs/`.** Это артефакт сборки. Правьте `src/build_site.py` или шаблоны.
6. **Не делайте автоматическую пересборку при правке шаблонов вручную в `docs/`** — деплой через GitHub Actions сделает это сам после `git push`.

## Аварская графика

Аварский — на кириллице с диграфами: **тӏ, лъ, гь, гъ, гӏ, кь, къ, кӏ, хь, хъ, хӏ, цӏ, чӏ**. В `src/build_site.py` есть аварский токенизатор: он считает каждый диграф одной буквой. Это важно:

- Алфавит в навигации содержит диграфы как отдельные «буквы».
- Подстраницы группируются по **трём аварским буквам** слова, поэтому `бет` и `бетӏ` оказываются на разных страницах (4 символа, но 3 буквы — третья «тӏ»).

### Правила нормализации палочки

`normalize_palochka()` (в `src/build_site.py` и в парсерах источников) приводит палочку к каноническому виду по этим правилам:

1. **Палочка может стоять только внутри аварского диграфа.** Основные основы, где палочка реально встречается: **т, г, к, х, ц, ч** (любого регистра) → тӏ, гӏ, кӏ, хӏ, цӏ, чӏ. Основы **л, п** (лӏ, пӏ) в аварском почти не встречаются — если что-то похожее на «лӏ»/«пӏ» попалось в тексте, это почти всегда не диграф (случайное совпадение, иноязычное слово, римское число и т. п.), а не повод автоматически лепить туда палочку; разбирать такие случаи вручную. Всё, что выглядит как палочка, но не следует за диграф-основой, — это не палочка.
2. **Регистр палочки совпадает с регистром основы:** строчная `ӏ` (U+04CF) после строчной буквы, заглавная `Ӏ` (U+04C0) после заглавной (`ГӀумру`, `гӏумру`, но не `Гӏумру` или `гӀумру`).
3. **Палочка может приходить разными глифами** в источнике: `Ӏ`, `ӏ`, `|`, `ǀ`, латинские `I`, `i`, `l` и даже цифра `1` (типист быстро печатает). Конвертируется в палочку только если следует за диграф-основой; иначе:
   - Палочка-глиф (`Ӏ`, `ӏ`, `|`, `ǀ`) вне диграфа — это ошибка типиста; меняется на цифру `1` (годы вроде `Ӏ993` → `1993`, нумерация `Ӏ классалдаса` → `1 классалдаса`).
   - Цифра `1` вне диграфа остаётся цифрой (`1993`, `11.08`, `1 класс`).
   - Латинские `I`, `i`, `l` вне диграфа и не приклеенные к цифре — не трогаются: это либо иноязычное слово, либо римское число (`том I`, `глава II`, `Осман I`). Приклеенные к цифре (`199I`) — ошибка типиста, меняются на `1` (`199I` → `1991`).
4. **Удвоение палочки в диграфе — типист дважды нажал клавишу.** После эмиссии палочки «съедаем» подряд идущие палочка-кандидаты (`чII` → `чӏ`, `т11` → `тӏ`, `кӏI` → `кӏ`).
5. **Римские числа — не диграф, даже если похожи.** Единственная диграф-основа, чей глиф совпадает с римской цифрой, — «х» (визуально = X), поэтому конфликт возможен только с диграфом хӏ. Если целое слово (между пробелами/пунктуацией) состоит только из «Х» и палочка-похожих символов — это римское число: «единицы» внутри него становятся латинской `I` («римская палочка»), не аварской палочкой и не цифрой; «Х» не трогаем. Примеры: `Х1Х` (типист печатал цифрами) → `ХIХ` (XIX век); `Х11` → `ХII` (том XII). Обычные аварские слова с диграфом хӏ (`хӀалтӏи`, `ХӀайдар`) этому правилу не подпадают — в них после хӏ идут обычные буквы, а не только Х/палочка-кандидаты.
6. **Другая нелатинская/некириллическая палочка-похожая буква своего языка не трогается и не путается с аварской.** Английский текст внутри аварского — латинская `I`; украинский — украинская `і`/`І`; и так далее для любого другого языка/алфавита. Правило 1 ограничивает замену на аварскую палочку строго аварскими диграфами — «до кучи» превращать в палочку всё подряд, что визуально похоже на вертикальную чёрточку, нельзя.

Для русско-аварского словаря (`ru-av`) исходный язык — русский, без диграфов. Используется стандартный русский алфавит.

## Поток работы

```
data/*.jsonl  ──►  src/build_site.py  ──►  docs/  ──►  GitHub Pages  ──►  sources.avar.me
                          ▲
                  src/templates/*
                  sources.json
                  books/*.pdf
```

1. Пользователь сообщает об ошибке в данных в чате [@avarme_chat](https://t.me/avarme_chat).
2. Админ правит соответствующую строку в `data/<source>.jsonl`.
3. **Добавляет запись в [`CHANGELOG.md`](CHANGELOG.md)** (см. ниже).
4. `git commit && git push` — Actions пересобирает сайт.
5. Другие сайты подтянут обновлённый jsonl при своей следующей сборке.

## Changelog (обязательно)

Любая смысловая правка данных (`data/*.jsonl`, `data/*.json`) **должна** сопровождаться записью
в [`CHANGELOG.md`](CHANGELOG.md): дата, краткое описание, затронутый источник (`av-ru`, `ru-av`, …)
и объём (число статей/строк). Новые записи — сверху. Это единственный человекочитаемый журнал
для потребителей данных (`forms`, `avar.me`, `corrector`, `index`); jsonl-дифф листать тяжело.

Для крупных/массовых правок дополнительно кладём подробный построчный diff в папку
[`changelog/`](changelog/) (`ГГГГ-ММ-ДД-<источник>-<тема>.md`) и ссылаемся на него из записи в
`CHANGELOG.md` — чтобы корректоры могли сверить каждую статью с источником. Формат строк:
`text[i]: «было» -> «стало»`, `- удалённый пример`, `+ добавленный пример (av = ru [метки] (коммент))`.

Служебные правки (сайт, шаблоны, CI, `docs/`) в changelog не заносим.

## RFI (Request For Improvement) от multilang.avar.me

`multilang.avar.me` — репозиторий локализации; его инструменты (LLM-ревью, `tools/expert_review.py` и др.) в фоне прогоняют русский текст `data/av-ru.jsonl` и копят замечания в `reports/request-for-improvement.jsonl` (со статусами `open`/`fixed`/`ignored`).

Чтобы затащить сюда непросмотренные замечания (запускается из `multilang.avar.me`):

```bash
cat reports/request-for-improvement.jsonl | grep -v '"status": "fixed"' | grep -v '"status": "ignored"' > ../sources/issues.av-ru.jsonl
```

`issues.av-ru.jsonl` — рабочий срез для текущего раунда разбора, не коммитится (не источник правды, не хранит историю). Можно удалять и перегенерировать заново перед каждым новым раундом.

Порядок разбора каждой записи:

1. Смотрим поле/слово/текст замечания, сверяем с `data/av-ru.jsonl` (и, если есть, с оригиналом словаря).
2. Реальная ошибка (опечатка, потерянная метка, структурный баг) — правим статью в `data/<source>.jsonl`, фиксируем раунд в [`CHANGELOG.md`](CHANGELOG.md).
3. Ложное срабатывание инструмента (законная лексика/грамматика, аварская графика, сравнение слова с собой и т. п.) — данные не трогаем, а добавляем запись в [`expert-review-av-ru-issues-2026-07-12-rejected.md`](expert-review-av-ru-issues-2026-07-12-rejected.md) (новый раунд), чтобы инструмент не поднимал его снова и мы не переразбирали то же самое. **Формат записи строго нормативный** — файл машинно разбирается `tools/expert_review.py`, см. [`expert-review-protocol.md`](expert-review-protocol.md) **перед** каждым раундом (не только один раз), особенно после того как раунд 7 (2026-07-13) его нарушил. Кратко:
   - один RFI = один блок `## #NNN — <слово>` (только `RFI.word`, без `(RFI-…)`, без «и <другое слово>», без комментариев в заголовке);
   - строго три отдельные строки: `- поле: `<RFI.field>`` / `- текст: «<RFI.current>»` / `- почему отклонено: <причина>` — никогда не склеивать `поле` и `текст` в одну строку;
   - никакого батчинга («RFI #091, #092, #093 …» одной прозой) — даже если причина одна и та же у N статей, на каждую свой полный блок;
   - если RFI был **прав** и источник действительно исправлен — это не «отклонено»; такие случаи не смешивать с блоками отклонения, а выносить в отдельную секцию «Исправлено в источнике (не false positive)» (см. §5 протокола) и обязательно отдельно фиксировать в `CHANGELOG.md`;
   - перед сдачей — прогнать чек-лист §7 протокола (в т. ч. `expert_review.py prepare --lang en` не должен ругаться `WARNING: skipping … missing поле/текст`).
4. Статус в `request-for-improvement.jsonl` руками не трогаем — `multilang.avar.me` сам увидит обновлённый `av-ru.jsonl` и закроет (`status: fixed`) починенные RFI при своей следующей синхронизации (`tools/workspace.py`).

**Апрув перед коммитом.** Правки `data/*.jsonl` не коммитятся без явного одобрения пользователя. Порядок: показать предлагаемый список правок (что и почему) → дождаться явного «да»/«коммить» → только после этого писать в файл и коммитить. Молчание или частичный отказ по одному пункту — это не согласие на остальные; если пользователь не подтвердил явно, коммит не делаем.

## Maintainer-RFI (dial-eval)

Замечания dial-eval / `llm-av-ru-review` приходят в `av-ru-maintainer-rfi.jsonl`
(рабочий файл в корне; после раунда очищается). Разбор — **через Cursor Canvas**
с тремя таблицами (отклонено / опечатки / структура), явной парой
«сейчас → предложение», char-level подсветкой diff и JSON «сейчас / предложение»
под строкой. В этом потоке правим только `data/av-ru.jsonl`; **`data/av-en.jsonl`
не трогаем** (его ведут другие мейнтейнеры).

Нормативный протокол: [`maintainer-rfi-canvas-protocol.md`](maintainer-rfi-canvas-protocol.md) —
читать перед каждым раундом. Не подменять canvas простынёй в чате без заполненных
предложений по каждой строке.

## Виды источников (`kind`)

В `sources.json` у каждого источника есть поле `kind`:

- **`dictionary`** — словарная статья на статью; формат `jsonl` (одна запись = одно слово). Сайт строит алфавит → 3-буквенные подстраницы со статьями в виде raw JSON.
- **`corpus`** — параллельный корпус (например, повесть `taras_bulba.json`). Формат `json` (массив элементов с `chapter`, `SentenceNumber`, `av`, `ru`). Сайт строит главу → страницу с параллельным `ru ↔ av` списком предложений; нумерация идёт по главам и `SentenceNumber`.

При добавлении нового источника указывайте правильный `kind` — это определяет, какая ветка сборки в `src/build_site.py` отработает.

## Решённые вопросы по схеме словарных статей (av-ru / ru-av)

Накопительный список вопросов о том, как оформлять то или иное содержимое в `senses[]`/`examples[]`, и уже принятых решений — чтобы не переоткрывать один и тот же вопрос и не расходиться в оформлении новых правок.

- **Вопрос:** «Буквально» (дословный перевод примера/идиомы) — это `label` в `example.labels` или `comment`?
  **Решение:** только `comment`, с префиксом `букв.`. Отдельного label `"буквально"` в словаре нет и не используется (0 вхождений против 1033 случаев `comment`, начинающегося с `букв.`).
  Примеры:
  ```json
  {"av": "бакрулав гӏадин вакизе", "ru": "отлупить как сидорову козу; отлупить как бакринца", "comment": "букв. представитель одного из мекканских племён"}
  {"av": "эбелалъ абурай ячинчӏого, авалалъул абурай яче", "ru": "не женись на той, о ком говорит мама [твоя], а женись на той, о ком говорят аульчане", "comment": "букв. квартал аула"}
  ```

- **Вопрос:** что делать, если `comment` (или `text`) по ошибке источника содержит аварский текст вместо русского?
  **Решение:** не переводить и не выдумывать за источник — оставить текст как есть, но пометить его происхождение полем `comment_lang` на том же уровне, что и `comment` (внутри объекта `sense`). Значение — код языка (`"av"` — пока единственное используемое). Если аварский текст попал не в `comment`, а в `text` (например в скобках вперемешку с русским переводом), его нужно вынести в `comment` + `comment_lang: "av"`, а `text` очистить до собственно русского перевода.
  **Порядок ключей (соглашение):** в объекте `sense` — `text → (precomment) → (labels) → (forms) → comment → (comment_lang) → (examples)`; `comment_lang` всегда сразу после `comment`, а `comment` — до `examples`, не в конце объекта. Для парсера это не важно, для глаз и диффов — да. При программных правках через `json.dumps` новый ключ иначе уезжает в конец — после добавления `comment` переставлять словарь в этот порядок.
  Примеры:
  ```json
  {"text": "интервью", "comment": "газет-журналалда бахъизе мухбирас цо лъилгунниги гьабулеб гара-чӏвари", "comment_lang": "av"}
  {"text": "стажёр; стажёрка", "comment": "жив ругьун гьавулев чи", "comment_lang": "av"}
  ```
  Схема поля документирована в `sources.json` → `schema.sense.comment_lang`.

- **Вопрос:** как распознать, что аварский глагол — «понудительная форма» (каузатив), если это не указано явно?
  **Решение:** по суффиксу `-забизе`/`-абизе` (иногда `-забизе`/`-лъизабизе` и т. п. — понудительный инфикс `-заб-`/`-аб-` перед окончанием инфинитива `-изе`). Пометка `"понудительная форма"` должна идти в `labels` того же `sense`, а не быть вписана как часть текста перевода. Если у понудительной формы есть парный непонудительный глагол в словаре, добавляется `see_also` с `kind: "from"` на него.
  Пример:
  ```json
  {"word": "капкикълъизабизе", "senses": [{"text": "доводить, довести до безденежья, нищеты", "labels": ["понудительная форма", "разговорное слово", "выражение"]}], "see_also": [{"target": "капкикълъизе", "kind": "from"}]}
  ```

- **Вопрос:** как оформлять аварское слово, когда оно на своём месте внутри русского `comment` (например, ответ на загадку, форма, от которой образовано слово)?
  **Решение:** брать в одинарные кавычки — так читатель сразу видит, что это аварское слово, а не русское. Применять везде, где встречается такой случай (не только к новым правкам, но и при следующей встрече со старыми).
  Примеры:
  ```json
  {"av": "бох ккун, бетӏер кьабулеб жо", "ru": "за ножку держать, головою ударяют", "labels": ["загадка"], "comment": "'квартӏа' молоток"}
  {"text": "меня", "comment": "направительный падеж от 'дун', в основном переводится падежными формами 'мне', 'на меня', 'до меня'"}
  ```

- **Вопрос:** нужно ли писать в `text` что-то вроде «от X», если статья и так уже помечена как производная форма через `labels` (например `"понудительная форма"`) и есть `see_also` с `kind: "from"` на базовое слово?
  **Решение:** в `text` — нет. Пишем `comment: "от 'X'"` (с кавычками) и оставляем `labels` + `see_also` kind `from`. Для повелительного и т. п. морфопомету можно кратко дописать после базы (`от 'X'; повел.`). Для **родительного** stub предпочтительна полная формула (как у других падежных comment): `родительный падеж от 'X'` (+ `genitivefrom` / `see_also` from).
  Пример:
  ```json
  {"word": "гьенкьезабизе", "senses": [{"comment": "от 'гьенкьезе'", "labels": ["понудительная форма", "учащательная форма"]}], "see_also": [{"target": "гьенкьезе", "kind": "from"}]}
  {"word": "кун", "senses": [{"comment": "от 'квине'; повел."}], "see_also": [{"target": "квине", "kind": "from"}]}
  {"word": "измуралъул", "senses": [{"genitivefrom": "измур", "comment": "родительный падеж от 'измур'"}], "see_also": [{"target": "измур", "kind": "from"}]}
  ```

- **Вопрос:** как оформлять абстрактные имена на `-лъи` (бывшие `"text": "от X", "comment": "абстр имя"`)?
  **Решение:** `text` не нужен; в `comment` полная формула с кавычками вокруг базы: `абстрактное имя от 'X'`. Обязателен `see_also` с `kind: "from"` на базовое слово (именительный, не родительный: `'футболист'`, не «футболиста»). Краткие пометы `абстр имя` / `абстр.` больше не используем.
  Пример:
  ```json
  {"word": "реакционерлъи", "senses": [{"comment": "абстрактное имя от 'реакционер'"}], "see_also": [{"target": "реакционер", "kind": "from"}]}
  ```

- **Вопрос:** как оформлять производные статьи-указатели без самостоятельной глоссы (`"text": "от бакӏ"` и т. п., не абстрактные `-лъи` и не глаголы с `labels` понуд./учащ.)?
  **Решение:** `text` не нужен; `comment: "от 'X'"` (кавычки), плюс `see_also` kind `from` на базу в именительном. Не смешивать в `text` грамматические хвосты вроде «местнп. послелог» — выносить в `comment` рядом с реальным переводом отдельного sense.
  Пример:
  ```json
  {"word": "бакӏалда", "senses": [
    {"comment": "от 'бакӏ'"},
    {"text": "вместо, за, взамен", "comment": "кого-чего-либо; местный падеж; послелог"}
  ], "see_also": [{"target": "бакӏ", "kind": "from"}]}
  ```

## Что менять, а что нет

| Хочется поменять | Куда лезть |
|------------------|-----------|
| Опечатку в слове | `data/<source>.jsonl` (найти `word: ...`) |
| Перевод / пример | `data/<source>.jsonl` |
| Опечатку в корпусе | `data/<source>.json`, найти запись по `chapter` + `SentenceNumber` |
| Новый источник | Добавить запись в `sources.json` + положить файл в `data/` |
| Внешний вид сайта | `src/templates/styles.css`, `src/templates/app.js` |
| Логика рендера страниц | `src/build_site.py` |
| Список словарей на главной | автоматически из `sources.json` |
| Доменное имя | `CNAME` |
| Деплой | `.github/workflows/deploy.yml` |

## Стиль

- Сайт — статический. Никакого SSR, никакого билд-инструмента сложнее одного python-скрипта. Никаких внешних JS-зависимостей через npm. Шрифты через Google Fonts (как в `index.avar.me`).
- Никаких эмодзи в шаблонах и текстах. Кроме SVG `☀` в favicon — он часть бренда avar.me.
- Сохраняйте дизайн в линии с [index.avar.me](https://index.avar.me) и [dev.avar.me](https://dev.avar.me): мягкий кремовый фон, цвет акцента `--accent: #9a7b1a`, шрифты Onest (UI) + Literata (заголовки и сериф).

## Когда сомневаетесь

Спросите перед тем как:

- Делать массовые замены в `data/*.jsonl` (regex по всему файлу).
- Менять формат данных (новые/убирать поля).
- Удалять записи.
- Менять имена путей или URL — это сломает потребителей (forms, avar.me, corrector).
