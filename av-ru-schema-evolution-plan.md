# Развитие схемы av-ru: два этапа

Дата: 2026-09-30. Статус: проект для ревью, не действующая схема.

Этот документ фиксирует обсуждённое направление и вопросы, которые нужно
решить до реализации. Он не разрешает автоматическую миграцию данных.
Текущие схемы и правила остаются действующими до принятия новой версии.

## Область применения и источники

Общая схема предназначена для словаря 2006 года, дополнений avar.me и
готовящегося словаря 1967 года. Метаинформация OCR из рабочего файла 1967
не становится частью публикуемой схемы автоматически.

Правим исходники:

- `data/av-ru.2006.jsonl`;
- `data/av-ru.avar.me.jsonl`;
- будущий `data/av-ru.1967.jsonl` после приёмки.

`data/av-ru.jsonl` — результат `python3 src/build_dictionaries.py`.
Приоритеты задаёт `dictionary-build.json`: сейчас 2006, затем avar.me.
Для совпавшего `word` выбирается весь набор статей первого источника;
значения между источниками не смешиваются. Подключение 1967 и его приоритет —
отдельное решение, не следствие изменения схемы.

Нормативные документы, которые потребуется обновить:
`schemas/av-ru.schema.json`, `schemas/av-ru.md`, описание схемы в
`sources.json`, `CLAUDE.md`, `README.md` и применимые правила `.cursor/rules/`.
Изменения ru-av рассматриваются отдельно: перенос правил туда не подразумевается.

## Этап 1. Структурировать уже существующие сведения

Включает только `literally`, унификацию ссылок и типизированные формы.
`id`, хеши, `cefr`, `origin` на этом этапе не вводятся.

### 1. Буквальный перевод: `literally`

Предложение: необязательная непустая строка в `sense` и `example`.
Содержит дословный перевод без префикса `букв.`. В av-ru язык — русский.
Помету «букв.» добавляет приложение при отображении.

До:

```json
{"text": "грязнуля", "comment": "о мужчине; букв. чёрт в саже"}
```

После:

```json
{"text": "грязнуля", "comment": "о мужчине", "literally": "чёрт в саже"}
```

Правила миграции:

- Сохранять основной перевод и все пояснения. Удалять `comment` только если
  после переноса он действительно пуст.
- Не переносить механически весь хвост после `букв.`: за дословным переводом
  могут следовать пояснения. Неоднозначные границы требуют ручного разбора.
- Случаи, где буквальный перевод одновременно является основным переводом,
  могут сохранять одинаковый текст в `text`/`ru` и `literally`.
- Сохранить ранее одобренные основные переводы, включая `подкувшинник` и
  `речное яйцо`; новая миграция не переоткрывает редакционные решения.
- `comment_lang` относится только к `comment`. При удалении `comment`
  нельзя оставлять сиротский `comment_lang`.
- Не вводить `literally_lang` без реальной потребности. Если найдётся
  буквальное пояснение на другом языке, вынести его на отдельное ревью.

### 2. Ссылки: `links[]`

Предложение: единый массив объектов вместо отдельных `*from`, `*for`,
`*to` и `see_also`. Единственная связь тоже записывается массивом.

```json
{
  "links": [
    {"word": "измур", "type": "genitive_of"},
    {"word": "другое слово", "type": "see"}
  ]
}
```

`word` — цель ссылки. Тип `genitive_of` означает: текущая статья/значение
является родительным падежом целевого слова. Направление каждого типа
нужно описать явно; нельзя судить о нём только по имени старого поля.

Общие связи находятся в статье, связи конкретного значения — в
`senses[].links`. Перенос уровня допускается только после проверки смысла.
На этапе 1 цель различается по слову и существующим уточнениям, без новых id.

Предварительное соответствие:

| Старое поле | Предлагаемый `type` | Условие |
|---|---|---|
| `genitivefrom` | `genitive_of` | Проверить направление на выборке |
| `dativefrom` | `dative_of` | То же |
| `ergativefrom` | `ergative_of` | То же |
| `locativefrom` | `locative_of` | Не смешивать разные местные формы |
| `ablativefrom` | `ablative_of` | Проверить смысл местной формы |
| `pluralfor`, `pluralfrom` | `plural_of` | Подтвердить эквивалентность обоих полей |
| `masdarfrom` | `masdar_of` | Проверить направление |
| `participlefrom` | `participle_of` | Не потерять временные уточнения |
| `see_also`, `kind: see` | `see` | Сохранить уточнения цели |
| `see_also`, `kind: from` | `derived_from` | Предпочесть более точный тип, если подтверждён |
| `forceto`, `masdarforceto` | Решить на ревью | Возможны разные отношения и направления |
| `deverbfrom`, `casefrom` | Решить на ревью | Сначала установить действующую семантику |
| `pastfrom`, `futurefrom` в рабочем 1967 | Решить на ревью | Учесть при согласовании общей схемы |

Существующие `refwordnum`, `comment`, `comment_lang`, `link_helper`
нельзя потерять. Их представление внутри новой связи нужно определить
по реальным данным. `refwordnum` сейчас может содержать несколько номеров;
не превращать его молча в индекс нового массива `senses`.

`link_helper` может встречаться как отдельное поле значения и как уточнение
ссылки. На ревью определить, является ли это уточнением `word` или отдельным
отношением; не переносить автоматически одним правилом.

После миграции не хранить одинаковую связь одновременно в старом поле и
`links`. Совпадение целей при разных типах или номерах значения не означает
дублирование. Самоссылки и отсутствующие цели отдельно проверяются, но
не удаляются только на основании автоматического флага.

### 3. Типизированные формы: `forms_dict`

Предлагаемый формат: объект, каждое значение — непустой массив объектов.
Минимальный объект формы содержит только `word`; дополнительные признаки
необязательны и заполняются только по подтверждённым данным.

```json
{
  "forms_dict": {
    "genitive": [
      {"word": "авторасул", "class": "I", "number": "singular"},
      {"word": "авторалъул", "class": "II", "number": "singular"}
    ],
    "imperative": [
      {"word": "гъа"},
      {"word": "гъе"}
    ]
  }
}
```

Это рабочее предложение для ревью. Оно заменяет предварительную идею
вложенности `singular → genitive`: число и класс находятся в объекте формы,
поскольку нужны и для падежных, и для глагольных форм.

Правила:

- Не использовать попеременно строки и массивы, не создавать ключи
  `genitive_1`, `genitive_2` для количества вариантов.
- Разные грамматические классы не объявлять взаимозаменяемыми вариантами.
  Класс задавать явно, когда он установлен; не угадывать по окончанию.
- Два допустимых варианта одной категории — два объекта с одинаковыми
  признаками и разными `word`.
- Формы, относящиеся только к конкретному значению, размещать в
  `senses[].forms_dict`. Семантику сосуществования с полем статьи утвердить:
  рекомендуемый вариант — общие формы плюс формы данного значения.
- Отсутствие категории означает «не записано», а не «форма невозможна».
- Пустые массивы и объекты не записывать. Не хранить несколько форм через
  запятую, «и» или другую текстовую склейку внутри `word`.
- Допустить отдельный `stress` в объекте формы по правилам статьи;
  точное определение позиции закрепить ссылкой на существующую схему.
- Встроенные ударения и графику рабочего 1967 нормализовать при приёмке,
  а не считать нормативным представлением нового поля.

Нужен закрытый словарь ключей и признаков. Минимальные кандидаты:
`nominative`, `ergative`, `genitive`, `dative`, `locative`, `ablative`,
`present`, `past`, `future`, `imperative`, `participle`.
Старый `plural` требует решения: это множественный именительный или форма
множественного числа без установленного падежа? `general` из 1967 также
нельзя автоматически приравнивать к `present`.
Для местных падежей нужно определить, достаточно ли `locative` или нужны
признаки локализации и направления. Не терять эти различия при унификации.

### 4. Совместимость с `forms[]`

`forms[]`, `gender_forms[]`, `spelling_forms[]` имеют существующих потребителей.
На первом этапе не удалять их без согласованного перехода.

Рекомендация для `forms[]`:

- Сохранять пока не классифицированные формы 2006 в исходном `forms[]`.
- При сборке добавлять в поисковый список формы из `forms_dict` статьи и
  значений, исключая точные повторы и сохраняя стабильный порядок.
- Не выводить из этого списка автоматически `gender_forms` или
  `spelling_forms`: они обозначают другие отношения.
- Не поддерживать вручную копии каждой типизированной формы в двух местах.

Таким образом, частично заполненный `forms_dict` не приводит к потере
оставшихся форм. На ревью проверить, нужен ли объединённый `forms[]` также
в публикуемых отдельных источниках, а не только в сводном словаре.

### 5. Порядок реализации первого этапа

1. Утвердить форму объектов, перечисления типов и правила отсутствующих полей.
2. Подготовить примеры миграции: буквальный перевод с пояснением; две ссылки;
   омоним; две формы одного падежа по классу; варианты одной категории;
   формы разных значений; частично классифицированная парадигма 2006.
3. Согласовать спецификацию с командой 1967 до приёмки их файла.
4. Обновить JSON Schema, описание полей и инструкции. Решить, где фиксируется
   версия схемы первого этапа; это версия формата, не ревизия статьи.
5. Сделать предварительный отчёт миграции без записи данных: все изменения,
   неоднозначные случаи и влияние на потребителей.
6. После ревью мигрировать исходники точечно, сохранить changelog и подробный
   diff. Не переносить OCR-метаданные в опубликованные статьи.
7. Обновить сборку и представление полей для приложений/сайта. Если нужна
   временная совместимость, создавать её сборкой, а не двойным ручным учётом.
8. Проверить результат и только затем готовить коммит и публикацию.

Критерии готовности:

- Новые поля проходят JSON Schema; языковые и морфологические правила
  проверяются отдельно от структуры.
- Не потеряны перевод, пояснения, формы, цели и уточнения ссылок.
- Все однозначные буквальные переводы находятся в `literally`; остатки помет
  учтены в отчёте, а не молча выброшены.
- Из исходников воспроизводится сводный файл; повторная сборка не меняет его.
- Стабильны порядок омонимов и число статей, если отдельно не одобрена их правка.
- Проверено разрешение ссылок через `word`, `forms`, `gender_forms`,
  `spelling_forms` и необходимые уточнения; новые формы доступны поиску.
- Потребители знают дату и формат перехода, а команда 1967 получила тот же контракт.

## Этап 2. Идентичность, контроль изменений и новые сведения

Этот этап отложен. Ниже — зафиксированное направление, не утверждённый контракт.

### 1. Постоянные `id`

Предложение: независимые пространства идентификаторов исходников:

```json
{"id": "av-ru.2006:000001", "source": "av-ru.2006"}
```

Также `av-ru.1967:000001` и `av-ru.avar.me:000001`.
Префикс берётся из идентификатора источника в реестре, а не обязательно
из значения поля `source` (у дополнений сейчас `avar.me.2026`).

Номер выдаётся один раз, не зависит от строки, заглавного слова или сортировки.
Омонимы имеют отдельные id. Исправления не меняют id; удалённые номера не
используются повторно. Сборка сохраняет id исходника.

До реализации решить: хранение счётчика, параллельное выделение номеров,
разделение/слияние статей и судьба ссылок на удалённые статьи. Рассмотреть
локальные постоянные id значений, если ссылки должны точно указывать на них.

### 2. Хеш содержимого

Предложение: `content_sha256`, автоматически вычисляемый сборкой.
Хеш обозначает состояние; id — идентичность. При исправлении id сохраняется,
хеш меняется. Числовую ревизию статьи пока не вводить: история есть в Git.

Хешировать весь опубликованный словарный объект: переводы, примеры, формы,
связи, пометы, комментарии, `literally`, `cefr`, `origin`, `source`.
Исключать сам хеш, id, технические даты, историю обработки и OCR-метаданные.
Уточнить исключения для вложенных id и идентификаторов целей ссылок: замена
цели является смысловым изменением и должна отражаться в хеше.

Считать по каноническому JSON: сортировать ключи объектов, сохранять порядок
массивов, не учитывать пробелы сериализации. Скрыто не исправлять строки.
Утвердить точные правила кодировки и сериализации, `hash_version` и тестовые
векторы для одинакового результата у всех команд.

Выбрать место публикации: отдельный автоматически собранный индекс или поле
в публикуемой статье. Не поддерживать хеши вручную в исходниках.
Версия схемы, версия алгоритма хеша и состояние статьи — разные вещи.

### 3. `cefr`

Предложение: необязательный enum `a1`, `a2`, `b1`, `b2`, `c1`, `c2` на уровне
значения. Разные значения одного слова могут иметь разные уровни.
Отсутствие означает «не оценено». До заполнения определить редакционную
методику оценки и не представлять её как официальную сертификацию.

### 4. `origin`

Языковое происхождение отделяется от `source` — словаря-источника.
Предлагаемая структура:

```json
{"origin": {"language": "ar", "word": "исходное слово", "via": ["tr"]}}
```

`language` — первоначальный язык, `word` — необязательный этимон,
`via` — необязательный массив языков-посредников в установленном порядке.
Согласовать стандарт кодов языка: например, `av`, `ru`, `ar`, `fa`, `tr`;
общие обозначения «тюркское» и конкретный турецкий не эквивалентны.

Обычно поле относится к статье; перенос на уровень значения требует
этимологического основания. Неизвестное происхождение — отсутствие поля,
а не автоматически `av`. Спорные этимологии требуют отдельного оформления.

### 5. Ссылки после появления id

Рассмотреть необязательные `entry_id` и идентификатор целевого значения
в объекте `links`. Если указаны и слово, и id, проверять их согласованность.

Конкретная исходная статья и слово в сводном словаре — разные цели.
Если приоритет источников скрывает статью в сборке, нельзя молча подменять
её id идентификатором победившего омонима. Правила разрешения и отображения
таких ссылок нужно согласовать до внедрения id.

## Переход потребителей: принятое направление

После обсуждения выбран замороженный последний выпуск старого формата,
а не постоянная генерация двух схем. Исходники мигрируют на новую схему;
старые мобильные манифесты и архивы остаются доступны, но больше не получают
новых редакционных выпусков. Новые приложения используют отдельный канал v2.

Подробный план, порядок переключения и задачи команд:
[plans/schema-v2/README.md](plans/schema-v2/README.md).

Канал v2 предназначен для обоих этапов. Поля второго этапа вводятся как
необязательные; клиенты игнорируют неизвестные поля. Несовместимая смена
типов или смысла существующих полей потребует отдельного решения.

Проверка локального кода показала: dev/ru читают JSONL при сборке, бот —
при обновлении словаря, ios/android превращают JSONL в SQLite, а мобильные
приложения читают эту базу. Версии развёрнутых сервисов и магазинных сборок
нужно сверить при выпуске последнего v1.

## Что пока не включать

`pronunciation`/IPA можно рассмотреть при появлении данных, но сейчас это
не обязательная часть ни одного этапа. Новые поля тематики, регистра и
диалекта не добавляем параллельно `labels` без отдельной потребности.
Сначала унифицируем существующие категории и избегаем двойного учёта.

## Вопросы для ближайшего ревью

1. Утверждаем ли имя `links` и массив объектов на обоих уровнях?
2. Какие точные типы заменяют все старые морфологические поля, особенно
   `forceto`, `masdarforceto`, `casefrom` и `deverbfrom`?
3. Как сохраняем целевые омонимы, исходную нумерацию значений и `link_helper`?
4. Утверждаем ли массивы объектов в `forms_dict`, признаки `class`, `number`
   и необязательный `stress`? Как кодируем классы и категории?
5. Как представляем множественный именительный, неуточнённый plural,
   местные падежи и глагольный `general`?
6. Как совмещаются формы статьи и отдельных значений; где собирается полный
   поисковый `forms[]` для отдельных источников и сводного словаря?
7. Какой переходный контракт получают потребители и команда 1967?

После ответов обновляем этот проект, утверждаем спецификацию первого этапа
и только затем готовим миграцию. Решения второго этапа остаются отложенными.
